## 2. 共通仕様

### 2.1 通信・データ形式

- 本番はHTTPS、ローカル開発ではHTTPを使用できる。
- JSON本文を送る場合は `Content-Type: application/json` を付ける。
- 応答はJSON。ただし204の応答には本文を付けない。
- JSONキーはcamelCase、IDは文字列、日時はISO 8601形式にする。
- 日時は `Z`、`+00:00` などのオフセット表記を許容する。小数秒の桁数を固定して解析しない。
- 日本時間の日付は `YYYY-MM-DD` とする。
- 未設定値は `null`、空の一覧は `[]`、件数がなければ `0` とする。
- 本書のJSON例にあるID・日時・進行状況は説明用であり、未確定のゲーム条件を決定するものではない。

### 2.2 認証

保護対象APIには次のヘッダーを付ける。

```http
Authorization: Bearer <sessionToken>
```

- ゲスト登録時にトークンを発行する。
- 現在の実装は32バイトの暗号学的乱数をbase64url形式にした値を使う。
- DBにはSHA-256ハッシュだけを保存する。
- トークンの一致・有効期限内・未失効の3点を確認する。
- トークンなし、形式不正、期限切れ、失効済みの場合は `401 UNAUTHENTICATED`。
- 操作対象の `userId` は認証済みセッションから取得する。クライアントに指定させない。
- キャラクターや善行の所有者を確認し、自分のデータだけを操作できるようにする。
- 現行コードのトークン有効期限は発行から90日。これは暫定実装で、正式な期限・更新方法は未確定。
- Flutterは `flutter_secure_storage` にトークンを保存する。初期リリースではトークン紛失時のデータ引き継ぎは提供しない。

### 2.3 エラー

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください。",
    "requestId": "00000000-0000-4000-8000-000000000099"
  }
}
```

`code` はアプリの処理分岐用、`message` は説明用。エラー内の `requestId` はサーバーが発行する問い合わせ用IDであり、善行投稿本文の `requestId` とは別物である。

| HTTP | code | 内容 | 状態 |
|---|---|---|---|
| 400 | `VALIDATION_ERROR` | 入力の型・値・項目が不正 | 登録・名前変更で実装済み |
| 401 | `UNAUTHENTICATED` | 認証情報なし・無効・期限切れ・失効 | 実装済み |
| 404 | `USER_NOT_FOUND` | ユーザーが見つからない | ユーザー情報取得・変更で実装済み |
| 404 | `CHARACTER_NOT_FOUND` | 対象キャラクターなし・他ユーザー所有 | 設計案 |
| 409 | `IDEMPOTENCY_CONFLICT` | 同じ善行requestIdで異なる内容 | 善行投稿では未実装 |
| 409 | `REQUEST_IN_PROGRESS` | 同じ善行requestIdの処理が進行中 | 設計案 |
| 409 | `CHARACTER_NOT_ACTIVE` | 投稿できないキャラクター状態 | 設計案 |
| 409 | `GENERATION_NOT_AVAILABLE` | 次世代作成可能日より前 | 設計案 |
| 409 | `ACTIVE_CHARACTER_EXISTS` | 育成中キャラクターが既に存在 | 設計案 |
| 422 | `DEED_NOT_VALID` | 善行として受け付けられない | 設計案 |
| 503 | `AI_UNAVAILABLE` | AI障害・タイムアウト | 設計案 |
| 500 | `INTERNAL_ERROR` | DB障害などで処理できない | 実装済み |

現状、壊れたJSONなど `express.json()` 自体のエラーと、未定義URLへの応答を上記JSON形式に統一する処理は未実装。

### 2.4 プレイヤー名の入力制約（実装済み）

- `displayName` は文字列で必須。
- 前後の空白を除去してから、長さ1〜20を確認する。
- 制御文字 `U+0000〜U+001F` と `U+007F` を含む名前は拒否する。
- 本文は `displayName` だけを受け付け、余分な項目は拒否する。
- 現行の長さ判定はJavaScriptの文字列長（UTF-16コード単位）。絵文字などは見た目の1文字が長さ2以上になることがある。

### 2.5 一覧の追加読み込み（設計案）

元の一覧に合わせ、善行履歴は `limit`・`offset` を使う。キャラクター履歴も同じ形式とする案。

| クエリ | 型 | 既定値 | 制約 |
|---|---|---:|---|
| `limit` | 整数 | 20 | 1〜50 |
| `offset` | 整数 | 0 | 0以上 |

```json
{
  "items": [],
  "totalCount": 0,
  "limit": 20,
  "offset": 0,
  "hasMore": false
}
```

`totalCount` は絞り込み条件に一致する全件数。続きは `offset + items.length` を指定する。途中で新規データが追加された場合は先頭から読み直し、アプリ側でもIDの重複を除く。既定値と上限は実装前に確認する。

## 4. 実装済みAPI

### 4.1 ゲスト登録

`POST /api/guests`

ユーザー・第1世代キャラクター・セッションを一つのDBトランザクションで作成する。

リクエスト：

```json
{
  "displayName": "たろう"
}
```

成功時：`201 Created`

```json
{
  "user": {
    "id": "00000000-0000-4000-8000-000000000001",
    "displayName": "たろう",
    "createdAt": "2026-10-24T03:00:00+00:00"
  },
  "currentCharacter": {
    "id": "00000000-0000-4000-8000-000000000002",
    "generation": 1,
    "imageId": "base_01",
    "hp": 100,
    "maxHp": 100,
    "totalXp": 0,
    "level": 1,
    "evolutionStage": 0,
    "status": "alive",
    "createdAt": "2026-10-24T03:00:00+00:00"
  },
  "sessionToken": "<発行されたランダムトークン>"
}
```

- `Idempotency-Key` ヘッダーは必須ではない。
- 現在は呼び出しごとに新しいユーザーを作る。同じ名前・同じ本文を再送しても、同じユーザーが返る保証はない。
- DBには登録要求の重複制御用テーブルとRPCの競合判定が残っているが、サービスは毎回内部キーを生成する。クライアント向けの再送保証ではない。
- `sessionToken` はこの応答で受け取って保存する。既存トークンを再取得するAPIはない。
- 現行の初期画像は `base_01`、初期レベルは1。画像IDの全種類・レベル計算式は未確定。
- 主なエラーは400・500。内部競合判定による409の分岐も残っているが、登録の再送保証として扱わない。

### 4.2 自分の情報取得

`GET /api/users/me`

Bearer認証必須。本文・クエリなし。

成功時：`200 OK`

```json
{
  "user": {
    "id": "00000000-0000-4000-8000-000000000001",
    "displayName": "たろう",
    "createdAt": "2026-10-24T03:00:00+00:00",
    "isGuest": true,
    "longestSurvivalDays": 1
  }
}
```

| 項目 | 型 | 意味 |
|---|---|---|
| `id` | string | ユーザーID |
| `displayName` | string | プレイヤー名 |
| `createdAt` | string | ユーザー作成日時 |
| `isGuest` | boolean | 初期リリースでは常にtrue |
| `longestSurvivalDays` | integer | 現在・過去を含む最長生存日数。キャラクターなしなら0 |

日本時間で作成日を1日目と数える。死亡なら死亡日まで、第2進化達成なら達成日まで数える。

現在は保存済みの状態・日付で計算する。未投稿ペナルティによる過去の死亡確定は未実装。ゲーム状態処理の導入時には、この集計前にも必要な状態確定を行う。

主なエラー：401、404 `USER_NOT_FOUND`、500。

### 4.3 プレイヤー名変更

`PUT /api/users/me`

Bearer認証必須。認証済みユーザーの名前だけを変更する。

リクエスト：

```json
{
  "displayName": "新しい名前"
}
```

成功時：`200 OK`

```json
{
  "user": {
    "id": "00000000-0000-4000-8000-000000000001",
    "displayName": "新しい名前"
  }
}
```

入力制約は2.4に従う。ユーザーID・作成日時・キャラクター・セッションは変更しない。

主なエラー：400、401、404 `USER_NOT_FOUND`、500。

### 4.4 稼働確認

`GET /api/health`

認証不要。本文なし。成功時：`200 OK`

```json
{
  "status": "ok"
}
```

Expressが応答できることを確認する。SupabaseやAIの接続確認は行わない。

### 5.1 キャラクター情報

```json
{
  "id": "00000000-0000-4000-8000-000000000002",
  "generation": 1,
  "imageId": "base_01",
  "hp": 100,
  "maxHp": 100,
  "totalXp": 0,
  "level": 1,
  "evolutionStage": 0,
  "firstEvolutionCategory": null,
  "secondEvolutionCategory": null,
  "secondEvolutionDate": null,
  "categoryPoints": {
    "kindness": 0,
    "environment": 0,
    "gratitude": 0,
    "courage": 0,
    "cooperation": 0,
    "honesty": 0,
    "selfCare": 0
  },
  "status": "alive",
  "createdAt": "2026-10-24T03:00:00Z",
  "diedAt": null,
  "endedAt": null,
  "endReason": null,
  "lifespanDays": 1,
  "deedCount": 0
}
```

| 項目 | 型 | 意味 |
|---|---|---|
| `generation` | integer | 世代。1から開始 |
| `imageId` | string | キャラクター画像ID |
| `hp` / `maxHp` | integer | 現在HP／最大HP |
| `totalXp` | integer | このキャラクターの累計XP |
| `level` | integer | レベル。計算式は未確定 |
| `evolutionStage` | integer | 0：初期、1：第1進化、2：第2進化 |
| `firstEvolutionCategory` / `secondEvolutionCategory` | stringまたはnull | 決定した属性のカテゴリID |
| `secondEvolutionDate` | stringまたはnull | 第2進化達成日の日本時間日付 |
| `categoryPoints` | object | 7属性のポイント |
| `status` | string | alive／dead／retired |
| `diedAt` | stringまたはnull | 実際の死亡日時 |
| `endedAt` | stringまたはnull | ゲーム上の育成終了日時 |
| `endReason` | stringまたはnull | death／second_evolution |
| `lifespanDays` | integer | 日本時間で数えた生存日数 |
| `deedCount` | integer | このキャラクターの善行総数 |

`endedAt` はゲーム上の終了時点を保存する設計案とし、遅れてAPIを呼んだ場合も処理実行日時で置き換えない。死亡なら死亡日時、第2進化なら達成日の翌日0:00とする。生存日数は作成日を含めて数えるため、終了日の判定には `diedAt`・`secondEvolutionDate` を使う。

ゲスト登録の応答は4.1の現在の形を維持する。上記全項目が登録APIにも追加済みという意味ではない。

### 5.2 今日の投稿状況

```json
{
  "date": "2026-10-24",
  "deedCount": 3,
  "earnedXp": 30,
  "xpLimit": 50,
  "remainingXp": 20,
  "goalAchieved": true
}
```

- 日本時間の日付で、有効な善行だけを数える。
- `earnedXp` はユーザー単位の当日獲得XP合計。キャラクターをまたいで集計する。
- `remainingXp` は `max(0, xpLimit - earnedXp)`。
- `goalAchieved` は「今日、有効な善行を1件以上投稿した」を表す。現在この判定を実装済み。

### 5.3 善行情報

```json
{
  "id": "00000000-0000-4000-8000-000000000003",
  "characterId": "00000000-0000-4000-8000-000000000002",
  "content": "道に落ちていたごみを拾った",
  "category": "environment",
  "praise": "周りをきれいにする行動、素敵だね！",
  "earnedXp": 10,
  "earnedCategoryPoints": 1,
  "recoveredHp": 0,
  "createdAt": "2026-10-24T03:10:00Z"
}
```

`recoveredHp` は実際に増えたHP。最大HP100・更新前HP100なら0、更新前HP90で回復量設定20なら10。報酬数値はAIではなくサーバーが決める。

## 6. ゲームAPI・追加予定APIの詳細

### 6.1 現在のキャラクター取得

`GET /api/characters/me`

Bearer認証必須。本文・クエリなし。未処理のペナルティ・死亡・育成終了を確定してから、最新世代を返す。死亡・育成終了後も、次世代未作成ならそのキャラクターを返す。

現在は基本情報・終了理由・生存日数・善行総数・今日の投稿状況・次世代作成可否を実装済み。上記の状態確定処理は未実装。終了理由・次世代作成可否は保存済みの状態・死亡日・第2進化達成日を基準に返す。

`currentCharacter.deedCount` はそのキャラクターの全期間の善行総数、`today.deedCount` はユーザー全体の今日の投稿件数を表す。

成功時：`200 OK`

| 応答項目 | 内容 |
|---|---|
| `currentCharacter` | 5.1のキャラクター情報 |
| `today` | 5.2の今日の投稿状況 |
| `canCreateNextCharacter` | 現時点で次世代作成が可能か |
| `nextCharacterAvailableOn` | 次世代作成可能な日本時間日付。条件未達ならnull |

第2進化当日はaliveで投稿可能、次世代作成は不可、作成可能日は翌日。死亡当日も次世代作成は不可で、死亡日の翌日から可能。

キャラクターが一体もなければ404 `CHARACTER_NOT_FOUND`。正常な登録では第1世代が同時作成される。

### 6.2 次世代キャラクター作成

`POST /api/characters`

Bearer認証必須。本文なし。次のどちらかを満たす場合に作成できる。

1. 前キャラクターが死亡し、日本時間で死亡日の翌日以降。
2. 前キャラクターが第2進化を達成し、日本時間で達成日の翌日以降。

前世代の必要な状態確定、条件確認、世代番号の加算、新キャラクター作成を一つのDBトランザクションで行う。ユーザー単位のロックとDB制約で同時作成を防ぐ。

新キャラクターはHP100・XP0・進化段階0で開始。過去の能力値は引き継がない。ユーザーID・名前・過去のキャラクターと善行履歴は保持する。

成功時：`201 Created`。`currentCharacter` に新キャラクターの情報（5.1）を返す。

育成中のキャラクターがいれば409 `ACTIVE_CHARACTER_EXISTS`、日付条件未達なら409 `GENERATION_NOT_AVAILABLE`。別リクエストが先に作成した場合も二体目は作らない。

追加の `Idempotency-Key` ヘッダーは要求しない案。

### 6.3 善行投稿

`POST /api/deeds`

Bearer認証必須。

リクエスト：

```json
{
  "content": "道に落ちていたごみを拾った",
  "requestId": "00000000-0000-4000-8000-000000000004"
}
```

| 項目 | 制約 |
|---|---|
| `content` | 文字列、前後空白除去後に空でないこと。上限500文字を暫定案とする |
| `requestId` | クライアント生成UUID。新規投稿ごとに作り、同じ投稿の再送では同じ値を使う |

元の一覧どおり本文は上記2項目を基本とする。`userId`・投稿先の `characterId` はサーバーが決める。投稿を受け付けたキャラクターに固定し、AI処理の途中で新世代へ付け替えない。

処理順：

1. 認証・入力検証。
2. ユーザー単位でrequestIdと内容を照合。確定済みの同じ投稿なら保存済み結果を返す。
3. 新規投稿は未処理日付を確認し、現在のキャラクターと投稿可否を確定する。
4. AIで有効性・7カテゴリのいずれか・褒め言葉を判定し、返却内容を検証する。
5. DBトランザクション内で、対象キャラクターが現在も投稿可能か再確認する。
6. 当日XP上限を確認して、HP・XP・属性ポイント・進化を更新する。
7. 善行と再送用の成功応答を同じトランザクションで保存する。

成功時：`201 Created`

| 応答項目 | 内容 |
|---|---|
| `deed` | 5.3の善行情報 |
| `xpLimitReached` | 処理後に当日XP上限へ達しているか |
| `evolution.changed` | この投稿で進化したか |
| `evolution.previousStage` | 投稿前の進化段階 |
| `evolution.currentStage` | 投稿後の進化段階 |
| `currentCharacter` | 更新後のキャラクター情報（5.1） |

再送・失敗時の規則：

- 成功済みの投稿と同じユーザー・同じrequestId・同じ内容なら、AIや報酬加算を再実行せず保存済みの成功応答を返す。HTTPも201を維持する案。
- 同じユーザー・同じrequestId・異なる内容は409 `IDEMPOTENCY_CONFLICT`。
- 内容比較では前後空白除去後の本文を使う案。
- 同じ投稿が処理中なら409 `REQUEST_IN_PROGRESS`。同じrequestIdで後から再試行する。
- AI障害で未確定なら再試行可能にし、報酬・善行履歴を確定しない。
- 確定済みの再送は、後で世代交代していても元の結果を返す。
- 善行として認められなければ422 `DEED_NOT_VALID`。
- 善行無効の確定結果も要求記録に保存し、同じ内容の再送には同じ422を返す案。善行履歴や報酬は作成しない。
- 死亡・育成終了・第2進化翌日以降の前キャラクターへの新規投稿は409 `CHARACTER_NOT_ACTIVE`。

AI応答待ちの間はDBトランザクションや行ロックを保持し続けない。投稿開始時と報酬確定時の両方でキャラクター状態を確認する。

### 6.4 善行履歴取得

`GET /api/deeds?limit=20&offset=0&characterId=<キャラクターID>`

Bearer認証必須。本文なし。

| クエリ | 必須 | 意味 |
|---|---|---|
| `limit` | 任意 | 取得件数。2.5に従う |
| `offset` | 任意 | 取得開始位置。2.5に従う |
| `characterId` | 任意 | 指定キャラクターの善行に絞る |

省略時はユーザーの全世代を対象にする。キャラクター詳細画面ではcharacterIdを指定する。所有者確認を行い、他人のID・存在しないIDはともに404 `CHARACTER_NOT_FOUND`。

新しい順（createdAt降順、同時刻はid降順）で返し、死亡・育成終了後も参照可能。

成功時：`200 OK`。2.5の一覧形式で、itemsは5.3の善行情報。totalCountは絞り込み後の善行総数。

### 6.5 今日の投稿状況取得

`GET /api/deeds/today`

Bearer認証必須。本文・クエリなし。成功時：`200 OK`。5.2の情報をそのまま返す。

XP上限後も投稿可能で、獲得XPは0。褒め言葉とHP回復は継続する。上限後の属性ポイント付与は未確定。

### 6.6 現在の進化状態取得

`GET /api/characters/me/evolution`

Bearer認証必須。本文・クエリなし。必要な状態確定後、最新世代の情報を返す。

成功時：`200 OK`

| 応答項目 | 型 | 意味 |
|---|---|---|
| `characterId` | string | 対象キャラクターID |
| `evolutionStage` | integer | 0／1／2 |
| `firstEvolutionCategory` | stringまたはnull | 第1進化属性 |
| `secondEvolutionCategory` | stringまたはnull | 第2進化属性 |
| `imageId` | string | 現在の画像ID |
| `totalXp` | integer | 累計XP |
| `nextEvolutionXp` | integerまたはnull | 次の進化に必要な累計XP |
| `remainingXp` | integerまたはnull | 次の進化までの残りXP |
| `categoryPoints` | object | 進化判定用ポイント。5.1と同じキー構成 |

第2進化後はnextEvolutionXp・remainingXpをnullにする。XP条件と集計範囲を決めてから実装し、未設定の条件を「次の進化なし」のnullとして扱わない。

死亡・育成終了後も次世代作成前は前世代の記録を返す。一体もなければ404 `CHARACTER_NOT_FOUND`。

### 6.7 歴代キャラクター取得

`GET /api/characters/history?limit=20&offset=0`

Bearer認証必須。現在と過去の自分のキャラクターを、世代の降順で返す。

成功時：`200 OK`。2.5の一覧形式で、itemsは5.1のキャラクター情報。totalCountは自分のキャラクター総数。空の一覧も200。

- 育成中は現在の進化形態、それ以外は最終の進化形態を返す。
- 思い出の殿堂と、選択したキャラクターの詳細表示に使う。
- 世代・レベル・属性・育成期間・善行総数・生存日数を含める。
- 善行本文の一覧は含めず、選択したIDで6.4を呼び出す。
- 詳細画面へ直接復帰する場合は履歴一覧から対象IDを探す案。専用の詳細取得APIが必要かは画面実装時に確認する。

### 6.9 退会・アカウント削除（追加予定）

`DELETE /api/users/me`

基本設計書の設定画面にある退会を実現する追加API案。Bearer認証必須。本文なし。

完了後、同じトークンでアクセスすると401。バックアップを含む保持方針・削除猶予の有無は別途決める。

## 7. ゲーム状態とDB整合性

### 7.1 日付・状態確定

キャラクター関連APIでは、未処理日付を確認してから応答する。善行投稿・次世代作成でも同じ状態確定処理を使う。

- ペナルティは、作成日の翌日から昨日までの終了済み日付を対象とし、有効な善行がない日だけに適用する。
- 作成当日、現在進行中の当日、第2進化達成日より後の日付は対象外。
- 同じ日付に二重適用しない。
- HPが0になった最初の日を実際の死亡日として記録する。後日APIを呼んだ日を死亡日にしない。
- 遡って死亡確定した場合も、次世代作成可能日は実際の死亡日の翌日で判断する。
- 第2進化達成日はaliveのまま、翌日以降にretiredにする。
- 育成終了日時は実際の終了時点を保存する。第2進化なら達成日の翌日0:00とする。
- 生存日数・世代交代可否は必要な状態確定後に計算する。

### 7.2 キャラクターの状態

| status | 意味 | 新規善行投稿 |
|---|---|---|
| alive | 育成中。第2進化達成当日も含む | 日付・HP等の確認後に可能 |
| dead | 死亡 | 不可 |
| retired | 第2進化による育成終了 | 不可 |

死亡キャラクターは復活させない。同時に育成できるのは一体。世代交代でもユーザーIDは変更しない。

### 7.3 報酬と進化

以下は基本設計書の仮設定である。

| 項目 | 値 |
|---|---:|
| 初期HP・最大HP | 100 |
| 初期XP | 0 |
| 善行1件のXP | +10 |
| 善行1件のHP回復設定 | +20（最大HPまで） |
| 善行1件の属性ポイント | +1 |
| 未投稿日1日あたりのHP減少 | -20 |
| ユーザー単位の1日XP上限 | 50 |

- XP上限は日本時間の日付・ユーザー単位で管理し、超える分は加算しない。
- 第1進化は7種類、第2進化は属性の順序を区別した49種類。
- 属性ポイント同点時は、該当カテゴリの最後の投稿時刻で判定する。優先方向・完全同時刻の場合の規則は実装前に決める。
- 第2進化当日は投稿と報酬付与を継続し、それより先には進化しない。
- HP・XP・属性ポイント・進化状態はサーバーだけが更新する。

### 7.4 同時実行への対応

- 同じユーザー・同じ善行requestIdの重複登録をDB制約で防ぐ。
- 当日XPの確認と加算を、一つのトランザクションで確定する。
- HP・XP・属性ポイント・進化・善行保存・再送用成功応答をまとめて確定する。
- ユーザー単位のロック等で、投稿と世代交代の競合を防ぐ。
- 次世代を重複生成しない。現在のDBには一ユーザー一体のalive制約がある。
- 善行は投稿時のキャラクターに紐付け、世代交代後も変更しない。
